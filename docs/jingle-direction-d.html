这一版和 A / B / C 的实质分歧（含两轮真实修正）

  1. 体积随需求变，没有手动折叠。0 待办时它在桌面上不存在。A 的信息密度被保留了，但作为菜单栏那一行，而不是一个常驻面板。
  2. 「卡住」和「做完」共用一个队列，但只有卡住会主动弹到你面前。第一版做法是两条通道完全分开、连视觉分区都不一样；用了之后发现对你来说两者其实是同一件事——都是要接手，区别只在接手时做什么（解决问题 vs 布置下一步）。所以现在合成一个「该我了」列表，用文字前缀区分「需要决定：」/「已完成：」，只有卡住保留主动弹窗——因为只有它的等待才真的在烧时间。
  3. 卡片上最大的字是「它说它干了什么」，本轮账退到第二行。被打断的那一刻，12m · +23.6k 不影响你「现在看还是待会看」的决定，那句话影响。所以账不删，但不许抢主位。
  4. 本轮账在 Work Unit 结束时结一次，不轮询。做完了和卡住了都算结束，都显示本轮 12m · +23.6k；还在跑的只显示已跑时长，也不计入上面「等你」的数字。分界线卡在成本上——时长是时钟相减，免费；token 要读日志，所以只在收尾那一刻算一次（末值 − 起始快照）。
  5. 人格绑项目，不绑 provider。你想的是「投研面板好了没」，不是「Codex 好了没」。而且 3 个 Codex 会话并行时，一张「Codex 员工」卡根本表达不了——B 在结构上装不下并行，而并行是这个产品的前提。provider 退成工牌角上那个小标记。
  6. 未映射项目默认只关心「卡住」，不逐条入队。第一次真实部署后发现：一个后台自动化项目（无人值守、一天跑几十次）产生的每条「做完了」都被当成需要你处理，队列直接刷屏、数字虚高。根因是把「done 也算该我了」这条规则套到了自动化项目上——现实是只有你显式在 projects.json 里认领过的项目，才默认「做完了也想让你知道」；没被认领的路径，默认只有真卡住才打扰你。
  7. 队列排序按紧急度，不按项目名字母序。同样是部署后发现的问题：排序曾经是按项目 id 字符串排的，跟"该先看哪个"完全无关。现在改成卡住的排最前，同类之间按等了你多久降序——这也是「怎么 focus」这个问题的直接答案。

这份 mockup 曾经和实现脱节过一次，现在补上了教训。最早那版方向 D 只画在一个独立分支上、从没并进 main，后续所有真正写代码的分支都是从没有这份文件的 main 拉出来的——实现的人压根打不开它，只能凭文字描述的规格重新发明视觉细节，这也是当时"做出来的东西和 mockup 完全不像"的直接原因。现在这份文件已经在 main 上，且内容同步了两轮真实修正（该我了合并、自动化项目默认策略、排序）。它能不能继续管用，取决于以后每次改动是不是先改这份文件、再让实现照着做——而不是先写代码、之后才想起来补图。

卡片上那句话的数据源已经验证过了，能拿到。不是数据库里那个 title（codex_spoken_notify.py:582 说得对，它经常是用户的第一句 prompt），而是会话 JSONL 里最后一条 assistant message 的正文——Codex 在 payload.type=="message"，Claude 在 message.role=="assistant"，两边都完整。首行裸取不够用（6 条实测里 3 条开头是「难度上，比较直观的排序是：」这种废话），过一次 DeepSeek 后 6 条里 5 条可直接上卡片，端到端 1.6–1.9s。剩下的风险是延迟：贴着 2 秒线没有余量，所以通知先出、摘要异步补写，别让播报等它。

全部为示例数据。「回到会话」和「已看」可以点，用来预览离队反馈——注意两者不同：「回到会话」才是真正的验收动作，「已看」是手动兜底。
